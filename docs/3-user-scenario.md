## 1. 작성 방침

- PRD 3장 입력 조건에 따라 인물 서사(페르소나)는 쓰지 않고 **사용 흐름 중심**으로 작성한다. 대상 세그먼트(학생 / 직장인 / 공통)는 맥락으로만 표기한다.
- 범위: MVP P0·P1 기능. P2(FR-15)와 범위 제외 항목(PRD 4.2, 도메인 정의서 6.1)은 다루지 않는다.
- 예시의 오늘(T)은 **2026-10-01**이며, 할일 A~F는 도메인 정의서 5.2 예시 데이터를 가리킨다.
- 공통 규칙 BR-01, BR-03, BR-11은 모든 시나리오에 적용되므로 "관련 ID"에서 생략한다 (해당 규칙이 흐름의 핵심인 경우만 표기).

## 3. 시나리오 상세

### SC-01 첫 가입부터 첫 할일 등록까지

| 항목      | 내용                                                                                                           |
| --------- | -------------------------------------------------------------------------------------------------------------- |
| 세그먼트  | 학생 (과제 마감을 기간으로 관리하려는 신규 사용자)                                                             |
| 사전 조건 | 계정 없음. 오늘 = 2026-10-01                                                                                   |
| 관련 ID   | UC-01, UC-02, UC-12, UC-05 / FR-01, FR-02, FR-05, FR-07 / BR-02, BR-05, BR-06, BR-07, BR-14 / AC-05-1, AC-05-2 |

**기본 흐름**

1. 사용자가 앱에 접속한다. 미인증 상태이므로 로그인 화면이 표시된다 (FR-04).
2. 회원가입 화면으로 이동해 이메일·비밀번호·이름을 입력하고 가입한다.
3. 계정과 본인의 '기본' 카테고리가 생성되고 로그인 화면으로 이동한다 (도메인 정의서 7.1).
4. 방금 가입한 이메일·비밀번호로 로그인한다. 목록 뷰가 표시되며 할일은 0건이다.
5. 할일 등록 화면을 연다. 카테고리 선택지에는 '기본'만 있고, 시작일자·종료일자는 2026-10-01로 채워져 있다.
6. 제목 "과제 제출"을 입력하고 종료일자를 캘린더에서 2026-10-03으로 고른 뒤 카테고리는 선택하지 않고 저장한다.
7. 할일이 '기본' 카테고리, 상태 '진행 중'으로 목록 뷰에 표시된다.

**대안·예외 흐름**

- 2a. 이미 가입된 이메일: 가입이 거부되고 오류가 안내된다 (BR-02). 입력값은 유지된다.
- 2b. 이메일 형식 오류, 비밀번호 정책 위반, 이름 공백 등 제약 위반: 위반 항목과 사유가 안내되고 입력값은 유지된다 (BR-11).
- 4a. 로그인 실패: SC-02 예외 흐름과 같다.

**기대 결과**

- 가입 당일 첫 할일 1건이 등록된다 (KPI-03 측정 대상 흐름).

### SC-02 로그인과 로그아웃

| 항목      | 내용                                                         |
| --------- | ------------------------------------------------------------ |
| 세그먼트  | 공통 (직장인은 업무 PC, 학생은 공용 PC에서 사용 후 로그아웃) |
| 사전 조건 | 가입된 계정 보유, 미인증 상태                                |
| 관련 ID   | UC-02, UC-11 / FR-02, FR-03, FR-04 / BR-01, BR-14            |

**기본 흐름**

1. 로그인 화면에서 이메일·비밀번호를 입력하고 로그인한다.
2. 인증에 성공하면 Access Token·Refresh Token이 발급되고(PRD 6.4) 목록 뷰가 표시된다.
3. 사용을 마치고 로그아웃을 선택한다.
4. Refresh Token이 폐기되고 쿠키가 삭제되며, 화면은 메모리의 Access Token을 버리고 로그인 화면으로 이동한다.

**대안·예외 흐름**

- 1a. 이메일이 없거나 비밀번호가 틀림: 어느 쪽이 틀렸는지 구분하지 않고 "식별자 또는 비밀번호가 올바르지 않습니다"만 안내된다 (BR-14).
- 1b. 같은 IP에서 분당 10회 넘게 실패: 로그인이 일시 거부된다 (NFR-11, P1).
- 4a. 로그아웃 후 앱 화면에 다시 접근: 로그인 화면으로 이동된다 (BR-01, FR-04).

**기대 결과**

- 로그인 시 목록 뷰에 진입하고, 로그아웃 후 새로고침해도 로그인 상태가 복구되지 않는다 (SC-03 예외 3a).

### SC-03 토큰 만료 자동 재발급과 새로고침 후 로그인 유지

| 항목      | 내용                                                               |
| --------- | ------------------------------------------------------------------ |
| 세그먼트  | 공통 (업무 중 탭을 띄워 두고 오래 자리를 비우는 직장인 등)         |
| 사전 조건 | 로그인 상태. Access Token 15분, Refresh Token 7일 (PRD 6.4, OI-03) |
| 관련 ID   | UC-11 (예외 3a), 전체 UC / FR-04 / BR-01                           |

**기본 흐름 A: 사용 중 Access Token 만료**

1. 사용자가 로그인 후 20분 동안 화면을 그대로 둔다. Access Token이 만료된다.
2. 돌아와서 '지연' 필터를 선택한다. 목록 요청이 401을 받는다.
3. 화면이 재발급을 1회 호출해 새 Access Token과 회전된 Refresh Token을 받고, 원래 목록 요청을 재시도한다.
4. 사용자는 재로그인 없이 필터 결과를 본다.

**기본 흐름 B: 새로고침·재방문**

1. 로그인 상태에서 브라우저를 새로고침하거나, 창을 닫았다가 다음 날 다시 접속한다.
2. 메모리의 Access Token이 없으므로 앱 시작 시 재발급을 호출한다.
3. 성공하면 로그인 화면을 거치지 않고 목록 뷰가 표시된다. 현재 탭·필터·캘린더 월 같은 UI 상태는 초기값(목록 뷰, 필터 '전체')으로 돌아간다 (가정: UI 상태는 Zustand 메모리에만 보관, PRD 7.1).

**대안·예외 흐름**

- A2a. 여러 요청이 동시에 401: 재발급 요청 1개를 공유하고 각각 재시도된다 (재사용 감지 오탐 방지).
- 3a. Refresh Token 만료(마지막 재발급 후 7일 초과, 가정), 로그아웃 후, 또는 쿠키 없음: 재발급이 실패하고 인증 상태·캐시를 비운 뒤 로그인 화면으로 이동한다.
- 3b. 이미 회전된 Refresh Token 재사용 감지: 해당 사용자의 Refresh Token이 모두 삭제되어 모든 기기에서 재로그인이 필요해진다.

**기대 결과**

- Refresh Token이 유효한 동안 사용자는 만료·새로고침을 의식하지 않고 계속 사용한다. 재발급 실패 시에만 로그인 화면으로 간다.

### SC-04 할일 등록 (카테고리 미지정, 날짜 검증)

| 항목      | 내용                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------- |
| 세그먼트  | 직장인 (업무 보고서 작성 기간 등록)                                                                                    |
| 사전 조건 | 로그인 상태. 오늘 = 2026-10-01. 카테고리 '기본', '업무' 보유                                                           |
| 관련 ID   | UC-12, UC-05 / FR-05, FR-07 / BR-06, BR-07, BR-08, BR-09, BR-13 / AC-05-1, AC-05-2, AC-05-3, AC-05-4, AC-05-5, AC-05-6 |

**기본 흐름**

1. 할일 등록 화면을 연다. 카테고리 선택지('기본', '업무')가 표시되고 시작일자·종료일자는 2026-10-01이다.
2. 시작일자 입력을 선택하면 캘린더가 표시되고, 고른 날짜가 입력된다 (브라우저 기본 날짜 입력, PRD 5.1).
3. 제목 "보고서", 설명(선택), 기간 2026-10-01 ~ 2026-10-03을 입력하고 카테고리는 비워 둔 채 저장한다.
4. 할일이 '기본' 카테고리, 상태 '진행 중'으로 저장되어 목록 뷰·캘린더 뷰에 반영된다.

**대안·예외 흐름**

- 3a. 카테고리 '업무'를 선택: '업무' 카테고리로 저장된다.
- 3b. 시작일자·종료일자 모두 2026-10-01: 하루짜리 할일로 저장된다.
- 3c. 시작일자 2026-10-02, 종료일자 2026-10-01: 저장이 거부되고 종료일자 오류가 안내되며 입력값이 유지된다. 화면 검증을 우회해도 서버에서 거부된다 (PRD 5.1).
- 3d. 제목이 공백만 있음, 또는 제목 100자·설명 1000자 초과: 저장 거부, 항목별 사유 안내, 입력값 유지.
- 3e. 시작일자가 오늘 이전(예: 2026-09-25): 허용된다 (OI-06). 종료일자도 지났다면 '지연'으로 표시된다.
- 3f. 다른 사용자의 카테고리 ID로 저장 요청: 저장이 거부된다 (BR-13).

**기대 결과**

- 카테고리를 고르지 않아도 할일은 항상 하나의 카테고리에 속하고, 날짜 규칙을 어긴 할일은 저장되지 않는다.
